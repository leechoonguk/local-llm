# s2 3.6:mtp REST 캡 60분 — 속도 vs 능력 분리 — sandbox (2026-08-25 UTC 08:14 / KST 17:14)

베이스라인에서 3.6:mtp REST 가 45분 캡 경계에 걸리는 게 **속도 문제인지 능력 문제인지** 가르기 위해, 레시피는 그대로(budget 5120) 두고 **셀 상한만 45분→60분**으로 올려 REST 만 n=2 재측정했다. 사용자가 허용한 "필요하면 하네스 수정"의 최소 개입(캡 파라미터)으로 원인을 분리한 실험. **결론: 캡을 올려도 게이트 초록이 보장되지 않는다 — REST 갭은 순수 속도가 아니라 모델의 능력 경계다.**

## 판단 (n=2, 5120 REST 누적 n=4 로 읽는다)
- **캡 상향은 REST 를 100% 로 만들지 못한다.** #1 은 60분 캡을 한참 남긴 **31.9분에 스스로 끝냈는데도 미완성 1** 로 실패했다. 시간이 부족한 게 아니라 모델이 "다 했다"고 판단하고 테스트 1개를 채우지 못한 채 종료했다. 반대로 #2 는 39.8분에 완주·초록. **더 준 시간이 원인이 아니다.**
- **5120 REST 누적 n=4 = 2/4 게이트 초록.**
  - 초록: baseline rep1(26m), cap60 rep2(39.8m) — 둘 다 회귀 0.
  - 실패: baseline rep2(45m 캡 타임아웃, 미완성 1), cap60 rep1(32m 조기 종료, 미완성 1).
  - **실패는 언제나 "미완성 1"(12~13/13 정답), 회귀는 4런 모두 0.** 파괴적이지 않고 딱 하나를 못 채우는 near-miss 다.
- **REST 는 로컬 모델의 능력 경계다.** 원인이 (a) 속도(타임아웃)와 (b) 조기 종료(마무리 누락) 둘 다이므로, 캡 상향은 (a)만 부분적으로 돕고 (b)는 못 고친다. 레시피(사고예산)는 `recipe-tb3072` 에서 낮추면 오히려 악화됨을 확인했다. 즉 **레시피로도, 캡으로도 REST 를 안정적 100% 로 못 만든다** — 3.6:mtp 의 REST 는 약 절반에서 초록, 실패해도 near-miss(미완성 1, 무회귀)인 지점에 있다.
- **integration 과 대비.** 같은 모델·레시피가 integration 은 반복해서 게이트 초록(별도 캠페인 2/2 + 로스터 밖 다수)인데 REST 는 ~50%. 과제 난도 차(정밀 복제 1건 vs 5계층 13건 신규)가 모델 능력 경계에서 갈린다.
- **기본 코더 레시피·캡 결정:** 코더는 3.6:mtp @ budget 5120 유지(repo 변경 없음). 벤치 셀 상한은 45분 표준 유지 — 60분으로 늘려도 REST 100% 가 안 되고 캠페인 시간만 늘어서, 캡 상향을 표준으로 채택할 근거가 없다(이 캠페인이 그 근거다).
