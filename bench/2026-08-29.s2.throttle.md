# s2 throttle — `check-verify` 스로틀 A/B와 integration 기준선: 스로틀은 지렛대가 아니다 (2026-08-29 08:02~10:59 KST)

계약 적용 후 첫 integration 셀이 2700초 TIMEOUT 으로 끝나자, 원인 후보로 지목된 **`check-verify` 실패 스로틀(30초→90초)** 을 단일 변수로 되돌려 같은 과제쌍을 다시 돌렸다. 결론: **스로틀은 원인이 아니다** — 30초 쪽이 오히려 두 과제 모두 TIMEOUT 이었다. 함께 얻은 것은 현재 구성의 **integration 기준선**(두 번 다 TIMEOUT)과, "첫 게이트를 8분 안에" 라는 브리핑 문구가 **데이터로 지지되지 않는다**는 확인이다.

## 조건
- Mac mini M4 Pro 64GB. 배포 구성(`omlx/Qwen3.6-35B-A3B-5bit:coder` 131072/8192, budget 2048, 코더 MTP off), aux 4B. 캡 2700s.
- 하네스: 프롬프트 단위 계약 4종 적용분(마감 비례화·프롬프트 간 상태·훅 경로 게이트·범위 존중). 두 캠페인의 **차이는 `FAILURE_THROTTLE_MS` 하나**(90s vs 30s).
- 반복 수: **각 조건 n=1**(과제당) — 이 게이트의 단발 분산이 크므로 방향 근거로만 쓴다.
- 발진 전 `make preflight` exit 0, 잔여 피험자 0 확인. `omp_touched` 는 4행 모두 0(피험자가 하네스를 건드리지 않았다).

## 판단 (각 n=1 — 잠정)
- **스로틀은 이 게이트의 지렛대가 아니다.** 30초로 되돌려도 integration 은 여전히 TIMEOUT(산출물 8/6 으로 오히려 적고 자체 게이트도 3회로 적었다), rest 는 90초에서 나온 최속 셀(1461s·15/15)과 달리 TIMEOUT(14/15) 이었다. 발견을 앞당긴다는 증거가 없고 비용(1회 1.8~7.7초의 실제 `make`)만 3배라 **90초를 유지**한다.
- **integration 은 현재 구성에서 두 번 다 TIMEOUT** 이다. 두 셀 모두 참조 파일 이름을 `search-barcode-item-info…` 대신 `search-barcode-item…` 으로 만들었고 끝까지 못 맞췄다. 이건 피드백 빈도 문제가 아니라 **이름 대조를 스스로 못 하는 문제**로 보인다(다음 캠페인 과제).
- **"첫 게이트를 8분 안에" 는 데이터로 지지되지 않는다.** 11행 풀링에서 ≤10분과 >10분 그룹의 소요 중앙(2804 vs 2783s)·산출물 중앙(14 vs 15)·TIMEOUT 비율이 사실상 같다. 역대 최속 셀(1461s)의 첫 게이트는 1062초(17.7분)였다. 그래서 OPENING-BRIEF 의 시간 기준을 **계층 단위**("한 계층이 서는 즉시, 끝에 몰아서가 아니라")로 바꿨다.
- 오늘의 유일한 개선 관측은 여전히 rest 의 contracts 셀(1461s·15/15·회귀 0)이며 n=1 이다. 셀 성능 판정은 반복이 쌓이기 전까지 유보한다.
