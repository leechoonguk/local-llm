# s2 stuck-reset 확장 v3 — 일반화 3레버, 첫 baseline 초과 (2026-08-26 KST 11:16)

v2(동률) 판정 후, 실패 모드별로 **도메인 하드코딩 없는** 일반 레버 3개로 재설계한 확장(`.claude/skills/llm-bench/ext/stuck-reset.ts`)의 검증. **REST n=2 = 2/2 게이트 초록·회귀 0 — baseline(1/2)·v2(1/2)를 처음 넘었다.**

레버(전부 제네릭, 처방 없음 — 무엇을 고칠지는 모델 자율):
1. **end-gate** — bash 결과에서 검증 실패(FAIL/ERROR 줄)를 관측하면 red 로 기록, 실패줄 없는 bash 성공이면 해제. red 인 채 프로즈-온리 턴(끝내려는 신호)이 나오면 turn_end 시점 `pi.sendUserMessage` 로 1회 재구동(상한 2). 실측 근거: agent_end 시점 재구동은 teardown 레이스로 0ms 빈 런(사망), turn_end 는 실제 생성으로 이어짐(프로브).
2. **자카드 유사도 thrash** — 3×완전동일 감지는 이 모델에 무용(변형 헤맴, v2 실측). 변이 툴(write/edit/patch/bash — read류 탐색은 연속 파일읽기 오발 때문에 제외)과 실패 시그니처에 토큰 자카드 ≥0.7 이 3회 연속이면 리셋.
3. **정체 리셋** — v2 의 맹목 주기(12턴) 대신, 성공한 변이 결과가 10턴간 0일 때만 리셋. 진행 중에는 안 끊는다.

리셋 = context 이벤트에서 messages 를 [시스템+중립 bootstrap+최근 4]로 재작성. 안전장치: 총 4회, 같은 계열 신호 지속 시 GIVE UP(강제하지 않음), 툴 정책 블록 제외. tool_result content 는 `[{type:"text",text}]` 구조라 텍스트 추출(contentText) 필수 — 이걸 빼먹으면 FAIL 줄시작 정규식이 안 맞는다(실측 버그 수정).

## 판단 (n=3, 확인 패스 1셀 중단)
- **v3 = 2/3 게이트 초록·회귀 0** — baseline(1/2)·v2(1/2)보다 우세한 추세이나 확정 전에 확인 패스를 중단(사용자 결정)해 통계적 확정은 아니다. 후속 검증은 체계화판 `ext/continuity.ts`(같은 3레버 + 위생 리셋 + todo 갱신 지시)의 자체 캠페인으로 잇는다.
- **end-gate 는 "필요할 때만" 이 실측됐다** — 이번 2셀은 모델이 스스로 초록까지 갔기에 0회 발동(마이크로테스트에선 red 종료 시 정확히 재구동). 보험으로 동작하고 평시에는 침묵한다.
